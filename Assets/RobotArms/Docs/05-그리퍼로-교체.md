# 5장 — 집게로 교체 (마찰로 잡기)

> **목표**: 4장과 **같은 과제**를 자석 대신 집게로 푼다.
> **핵심**: **물체를 붙잡는 코드를 전부 없앤다.** 손가락이 누르고, 마찰이 버틴다.
> **예상 시간**: 반나절

---

## 1. 딱 하나만 바꾼다 — 집는 방법

4장에서 과제는 이미 완성됐다. 5장은 **집는 방법만** 바꾼다.

| | 4장 (자석) | 5장 (집게) |
|---|---|---|
| **팔** | Transform으로 직접 회전 | **그대로** |
| 과제 | 집어서 옮겨 놓기 | **그대로** |
| 보상 | 진전 + 집기 `+0.5` + 놓기 `+1` + 놓침 `-0.3` | **그대로** |
| 액션 | 연속 3 + 이산 1 | **그대로** |
| 잡는 방법 | `SetParent` — 프로그램이 붙여준다 | **손가락이 눌러서 마찰로 버틴다** |
| 관측 | 16 | 19 |

> **팔은 건드리지 않는다.**
> 관절까지 물리로 바꾸면 한 번에 두 가지가 달라져서,
> 학습이 어려워졌을 때 어느 쪽 때문인지 알 수 없다.

### 없어진 코드

4장의 `Grab()` / `Release()` 가 통째로 사라졌다.

```csharp
// 4장 — 우리가 붙였다
targetObject.SetParent(arm.tip);
_objectBody.isKinematic = true;

// 5장 — 붙이는 코드가 없다. 물리가 알아서 한다.
bool nowHolding = gripper.BothTouching;
```

**"잡았다"가 우리가 정하는 값에서, 손끝으로 알아내야 하는 값으로 바뀌었다.**

## 2. 무엇을 붙이나

```
TrainingArea
├── RobotArm/Base/…/Tip          ← 1~2장 그대로. 손대지 않는다
└── Gripper                       ← 새로 만든다
    ├── Hand      Rigidbody(kinematic) + GripperHand + PincerGripper
    ├── FingerL   Rigidbody + HingeJoint + FingerContact   (빈 오브젝트, scale 1)
    │   ├── Upper     위마디 — 경첩에서 바깥으로 벌어지며 내려간다
    │   ├── Lower     아래마디 — 팔꿈치에서 꺾여 다시 안쪽으로 모인다
    │   └── Pad       패드   — 끝에서 물체를 무는 면 (어두운 색)
    └── FingerR   〃
```

손가락 하나가 **마디 세 개**로 되어 있다.
상자 하나로 만들면 집게로 보이지 않고, 무엇이 잡는 면인지도 알 수 없다.

```
        ● ●        경첩 — 손목 가까이, 안쪽
       ╱   ╲       위마디 — 바깥으로 벌어진다
      ▌     ▐      팔꿈치 — 가장 넓은 자리
       ╲   ╱       아래마디 — 다시 모인다
        ▓ ▓        패드 — 여기가 무는 면
```

**바깥으로 부풀었다가 끝에서 모이는** 이 모양이 집게(tongs)다.
경첩을 손목 가까이 둘 수 있다는 것이 덤이다 —
벌릴 때 회전 반경이 짧아져서, 입구는 더 넓어지는데 아래로는 덜 내려온다.

### 왜 하필 세 마디인가

두 마디로는 집게발이 안 된다.

- **바깥으로 부푼 모양**을 내려면 경첩보다 바깥으로 나가는 마디가 있어야 하고
- **물체를 제대로 물려면** 마지막이 물체와 나란한 평면이어야 한다

둘 중 하나를 빼면 집게발이 아니거나, 물체가 옆으로 밀려 나간다.
**집게 전체 게임오브젝트는 10개** — 이보다 더 줄이면 모양이나 성능 중
하나를 잃는다. (손바닥처럼 보이기만 하는 부품은 넣지 않았다)

> **손가락 뿌리는 스케일 1인 빈 오브젝트다.**
> 스케일이 있는 오브젝트에 자식을 붙이면 전부 찌그러진다.
> (1장에서 `Base`·`Tip`을 빈 오브젝트로 둔 것과 같은 이유)
>
> 덤으로 뿌리의 원점을 경첩 자리에 둘 수 있어서,
> `HingeJoint.anchor`를 그냥 `0`으로 두면 된다.

쓰는 부품은 **`Rigidbody` 와 `HingeJoint` 둘뿐**이다.
래그돌이나 흔들다리를 만들 때 쓰는 그것과 같다.

| 치수 | 값 | 무엇을 정하는가 |
|---|---|---|
| 경첩 / 팔꿈치 좌우 위치 | `±0.17` / `±0.27` | 집게발 실루엣 |
| 패드 좌우 위치 | `±0.115` | 안쪽 면 `0.095` = 물체 반폭을 문다 |
| 패드 구간 (경첩 기준 깊이) | `0.18` ~ `0.28` | 무는 면의 넓이 |
| 패드 앞뒤 폭 | `0.26` | **앞뒤 허용 오차** |
| 벌림 각도 | `50°` | **좌우 허용 오차** (5절) |
| **손가락 무게** | **`0.6` kg** | **잡히느냐 마느냐** (6절) |
| 쥐는 힘 / 속도 | `4` N·m / `90`°/s | |
| 마찰 (`PM_Grip`) | 정지 `2.0` · 운동 `1.6` · `Maximum` | 손가락에만 붙인다 |

## 3. ★ 집게를 팔의 자식으로 매달면 안 된다

가장 먼저 부딪히는 문제다. 그리고 원인이 눈에 보이지 않는다.

```
팔     — Transform을 직접 대입한다.  물리 엔진은 팔의 존재를 모른다.
집게   — Rigidbody다.                물리 엔진이 위치를 정한다.
```

집게를 `Tip`의 자식으로 두면, 팔이 회전할 때 손가락도 **끌려서** 움직인다.
그 이동은 물리 엔진 입장에서 **순간이동**이다.

> **순간이동하는 손가락은 물체를 "누르지" 못한다.**
> 통과했다 나타났다 할 뿐이다.
> 마찰은 **맞닿은 채로 미는 힘**에서 나오므로, 그러면 절대 잡히지 않는다.

### 해결 — 팔 바깥에 두고 따라가게 한다

```csharp
void FixedUpdate()
{
    _body.MovePosition(follow.position);    // transform.position = … 이 아니다
    _body.MoveRotation(TargetRotation);
}
```

`MovePosition`은 순간이동이 아니라 **"이번 스텝 동안 여기까지 움직여라"** 는 주문이다.
물리 엔진이 속도를 계산해서 옮기므로, **물린 물체도 같은 속도로 함께 딸려간다.**

## 4. ★ 손목이 없어서 "위에서" 집는다

이 팔에는 **손목 관절이 없다.** 어깨·팔꿈치·좌우 회전 셋뿐이다.
그래서 팔 끝의 기울기는 우리가 정하는 게 아니라 **끌려서 정해진다.**

실제로 계산해보면 이렇다.

```
테이블 위(높이 0.1)의 물체에 팔 끝을 대려면
  → 팔뚝은 약 62도 아래로 꽂히는 자세밖에 없다
  → 그 방향으로 손가락(0.22)을 뻗으면 끝이 테이블 아래로 들어간다
```

**즉 지금 구조로는 옆에서 집는 것이 기하학적으로 불가능하다.**
처음 만들었을 때 실제로 이렇게 됐다 — 손가락이 테이블을 파고들면서
물체를 밀어냈고, 잡기는커녕 30cm씩 굴러갔다.

### 해결 — 손목을 항상 아래로 고정한다

관절을 하나 더 다는 대신, 집게가 **늘 똑바로 아래**를 보게 한다.

```csharp
public static Quaternion AimRotation(Vector3 tipPosition, Vector3 basePosition)
{
    Vector3 flat = tipPosition - basePosition;
    flat.y = 0f;                                     // 좌우 방향만 팔을 따라간다
    return Quaternion.LookRotation(Vector3.down, flat.normalized);
}
```

그러면 집게가 팔 끝에 매달려 **위에서 내려 집는** 형태가 된다.

> 실제 로봇 팔도 바로 이 문제 때문에 손목 축을 둔다.
> 관절을 늘리지 않고 같은 효과를 얻은 것이다.

### 딸려오는 두 가지 조정

| 값 | 2장 | 5장 | 이유 |
|---|---|---|---|
| `clearance` (바닥 한계) | `0.07` | **`0.22`** | 집게가 팔 끝보다 `0.22` 아래까지 내려온다 |
| 거리 기준점 | 팔 끝 | **손가락 사이** (`GripCenter`) | 팔 끝을 물체에 맞추면 손가락은 테이블 속에 있다 |

## 5. ★ 손가락 모양 — 깔때기로 벌리고, 나란히 문다

처음에는 판을 그냥 옆에 달고 회전시켰다. **거의 안 잡혔다.**

```
회전하는 판을 그냥 달면 → 물체와 비스듬히 만난다
                        → 모서리로만 닿는다
                        → 누르는 힘이 물체를 옆으로 밀어낸다
                        → 수박씨처럼 튀어나간다
```

### 해결 — "다 오므린 자세"에서 거꾸로 설계한다

```
① 먼저 면이 물체와 나란해지는 자리에 패드를 놓는다  (중심 ±0.115)
② 거기서 통째로 바깥으로 50도 젖힌 것을 쉬는 자세로 삼는다
```

젖히면 패드가 통째로 바깥·아래로 돌아가면서 입구가 벌어진다.

| 벌린 자세 (손목 기준 깊이) | 간격 |
|---|---|
| 경첩 `0.00` | `0.340` |
| 팔꿈치 `0.00` | `0.621` |
| **패드 위 `0.15`** | **`0.556`** ← 가장 좁은 목 |
| 패드 끝 `0.22` | `0.714` ← 입구 |
| *오므려 나란해지면* | `0.190` ← 물체(`0.2`)를 문다 |

**즉 벌리면 깔때기, 오므리면 평행한 두 면이 된다.**

- 깔때기 → 어긋나 있어도 내려오면서 물체가 가운데로 밀려 들어온다
- 평행한 면 → 물체의 **납작한 면 전체**로 눌러서 옆으로 빠지지 않는다

### ★ 집게발 모양의 대가 — "목"이 생긴다

바깥으로 부풀었다가 모이는 모양은 보기엔 좋지만,
**팔꿈치와 패드 사이에 가장 좁은 목이 생긴다.**
물체는 이 목을 통과해야 들어올 수 있다.

처음 만들었을 때 벌림 각도를 그대로 뒀더니 목이 `0.487`밖에 안 됐고,
좌우 허용 오차가 `±0.18` → `±0.09`로 반 토막 났다.

| 바꾼 것 | 목 간격 | 잡히는 범위 (좌우) |
|---|---|---|
| 상자 하나 · 벌림 `38°` | — | `±0.18` |
| 집게발 · 벌림 `38°` | `0.487` | `±0.09` ← 목에 걸린다 |
| **집게발 · 벌림 `50°`** | **`0.556`** | **`±0.18`** |

> **모양을 바꾸면 반드시 다시 재봐야 한다.**
> 보기 좋아진 대신 조용히 성능이 반으로 떨어져 있었다.
> 더 벌리는 것으로 되돌렸고, 덤으로 손가락이 아래로 덜 내려오게 됐다
> (`0.303` → `0.216`) — 테이블에 걸릴 걱정도 함께 줄었다.

### 여기에 딸린 제약 — 손가락이 테이블에 닿으면 안 된다

벌린 손가락은 손목보다 `0.303` 아래까지 내려온다.
그래서 집는 높이(`GripDepth`)를 충분히 띄워야 한다.

| `GripDepth` | 집을 때 팔 끝 | 벌린 손가락 끝 | 오므리면 |
|---|---|---|---|
| `0.19` | `0.29` | `-0.013` | **각도 2° — 테이블에 걸려 못 닫힌다** |
| **`0.22`** | `0.32` | `+0.017` | 각도 37° — 정상 |

그리고 바닥 한계선(`clearance`)은 **`0.30`을 넘길 수 없다.**
어깨(J0·J1)가 높이 `0.30`에 있어서, 그보다 높이면 팔이 늘 "막힘"이 된다.
→ **손가락 길이는 이 상한이 함께 결정한다.**

물체(`0.2`)가 있으면 손가락은 나란해지는 자리에서 막혀 멈추고,
거기서 계속 민다. 그 미는 힘이 마찰의 재료다.

```csharp
motor.targetVelocity = (close ? 1f : -1f) * gripSpeed * closeSign;
motor.force = gripForce;       // "이 힘까지 써서" 그 속도를 내라
```

## 6. ★ 그래도 안 잡히면 — 마찰도 힘도 아니고 **무게**다

깔때기로 고친 뒤에도 물체가 자꾸 빠졌다.
마찰을 `1.2` → `2.0`으로 올려도, 쥐는 힘을 `1.5` → `10`으로 올려도
**들 수 있는 무게가 `0.2`kg에서 꼼짝도 하지 않았다.**

원인은 엉뚱한 곳에 있었다. **손가락이 너무 가벼웠다.**

```
물리 엔진은 무게 차이가 큰 두 물체를 관절로 잇는 것에 약하다.
가벼운 쪽이 무거운 쪽에 밀려나면서 계산이 흐트러진다.
```

손가락 무게만 바꿔가며 잰 결과다. (마찰·쥐는 힘은 그대로)

| 손가락 무게 | 들 수 있는 최대 무게 | 천천히 흔들기 |
|---|---|---|
| `0.05` kg | `0.2` kg | **빠진다** |
| `0.20` kg | `1.0` kg | 버틴다 |
| **`0.50` kg** | **`2.0` kg** | **버틴다** ← 이 값을 쓴다 |
| `2.00` kg | `2.0` kg | **빠진다** (자기 관성이 너무 커진다) |

> ### 여기서 배우는 것
> **물리가 이상할 때 계수부터 올리면 안 된다.**
> 마찰을 아무리 키워도, 힘을 아무리 키워도 안 되는 문제가 있다.
> 숫자를 하나씩 바꿔가며 **무엇이 실제로 결과를 바꾸는지** 재봐야 한다.
>
> 무게 비율은 물리 엔진을 쓸 때 늘 따라다니는 제약이다.
> 관절로 이은 부품끼리는 무게를 **10배 안쪽**으로 맞춘다.

### 마찰 재질은 손가락에만 붙인다

물체에는 붙이지 않는다. Combine이 `Maximum`이라 손가락이 닿는 순간
둘 중 큰 값(`2.0`)이 쓰이기 때문에 붙일 필요가 없다.

오히려 붙이면 **손해**다. 물체가 테이블에도 `2.0`으로 들러붙어서,
집게가 내려올 때 깔때기가 물체를 밀어 넣지 못한다.
(실측: 밀어준 거리가 `0.080` → `0.008`로 줄었다)

## 7. ★ 학습이 통째로 실패했다 — 그리고 고친 것

처음 만든 5장은 **800만 스텝을 돌려도 전혀 배우지 못했다.**
학습 로그가 남긴 증거는 딱 두 줄이었다.

```
Environment/Cumulative Reward   -1.00   (내내 변화 없음)
Environment/Episode Length      599     (한 번도 성공으로 끝난 적 없음)
```

시간 페널티를 "에피소드 내내 더하면 -1"이 되도록 설계했으니,
**보상 -1.00 = 진전 보상이 정확히 0** 이라는 뜻이다.
팔이 물체 쪽으로 한 발짝도 못 갔다.

### 원인 ① 바닥 한계선이 팔을 가뒀다

손가락이 테이블을 파고들지 않게 `clearance`를 `0.07` → `0.29`로 올렸는데,
**어깨가 높이 `0.30`에 있다.** 팔 전체가 `0.29~0.30` 사이의 얇은 층만
지나다닐 수 있게 됐고, 통과 방지는 관절을 하나씩 되돌리므로
그 좁은 통로를 빠져나가지 못한다.

| `clearance` | 스폰 25곳 중 접근 가능 |
|---|---|
| `0.07` ~ `0.22` | **25곳** |
| `0.26` | 23곳 |
| **`0.29`** | **10곳** ← 60%는 접근 자체가 불가능 |

> **이걸 놓친 이유가 더 중요하다.**
> 그때까지의 잡기 검증을 전부 `blockPenetration`을 **꺼놓고** 했다.
> 학습은 켠 채로 돌아갔다. **검증 조건이 실제 조건과 달랐다.**

### 원인 ② 보상이 "돌진하라"고 가르쳤다

보상은 손가락 사이와 물체의 거리를 줄이는 것이었다.
자석(4장)이라면 맞는 설계다. 아무 방향에서나 닿기만 하면 됐으니까.

**집게는 다르다.** 옆에서 직진하면 집게가 물체를 밀어낸다.
밀린 물체를 또 쫓아가고, 또 밀고 — 거리가 영영 줄지 않는다.

### 고친 것 — 과제를 네 토막으로 나눈다

```
① 잡으러 간다 — 물체 위로 간다. 수평이 맞으면 목표가 내려온다
② 들어올린다  — 물었으면 먼저 똑바로 든다
③ 옮긴다      — 놓을 자리 위로 간다. 수평이 맞으면 내려온다
④ 놓는다      — 손을 편다
```

단계마다 **가야 할 점 하나**가 정해지고,
보상 공식은 여전히 "그 점에 가까워진 만큼" 하나뿐이다. (4장의 철학 그대로)

```csharp
Vector3 Above(Vector3 spot)       // 수평으로 멀면 높이, 가까우면 낮게
{
    float lift = Mathf.Clamp01(HorizontalDistance(Mover, spot) / alignRadius) * hoverHeight;
    return spot + Vector3.up * lift;
}
```

이 한 함수가 **"위로 돌아 내려오는" 경로**를 저절로 만든다.

단계를 넘어갈 때마다 한 번씩 보너스를 준다. 없으면 다음 단계로 건너갈 다리가 없다.

| 단계 | 보너스 |
|---|---|
| ① 물었다 | `+0.5` |
| ② 들었다 (`0.40`까지) | `+0.5` ← **새로 추가** |
| ③ 놓았다 | `+1.0` |

### 관측도 하나 바꿨다 (개수는 그대로 19)

| | 4장 | 5장 |
|---|---|---|
| 3칸을 무엇에 쓰나 | 놓을 자리 위치 | **지금 가야 할 점** |

놓을 자리는 잡기 전에는 쓸모없는 정보였다.
**다단계 과제에서는 "무엇을 관측에 넣느냐"가 개수보다 중요하다.**

### 두 번째 학습 — 이번엔 보상이 -144까지 폭주했다

단계를 나눈 뒤 다시 돌렸더니 이런 곡선이 나왔다.

```
20,000 스텝   -1.29
80,000 스텝   -144.18     ← ?!
160,000 스텝   -75.64
320,000 스텝   -1.04       (다시 -1로 수렴, 여전히 성공 0회)
Losses/Value Loss  116 ~ 168   ← 가치함수가 따라가지 못한다
```

시간 페널티 총합은 `-1`이 최대인데 **-144**가 나왔다.

**원인: 에피소드를 끝내는 조건이 "성공" 하나뿐이었다.**

집게가 물체를 쳐서 테이블 밖으로 떨어뜨리면 물체는 계속 낙하한다.
목표까지의 거리가 매 스텝 멀어지니 진전 보상이 계속 큰 음수가 되고,
에피소드는 3000스텝을 꽉 채운다.

> **끝낼 수 없는 상황은 끝내줘야 한다.**
> 4장(자석)에는 이 문제가 없었다. 자석은 물체를 밀지 않으니까.
> 집는 방식을 바꾸면 **에피소드 종료 조건도 다시 봐야 한다.**

### 안전장치 세 개를 넣었다

| 장치 | 하는 일 |
|---|---|
| **물체 분실 종료** | 테이블 아래로 떨어지거나 팔이 닿을 수 없는 곳으로 가면 `-0.5` 주고 끝낸다 |
| **한 스텝 보상 상한** | 진전 보상을 `±0.05`로 자른다. 튀는 한 스텝이 에피소드 전체를 덮지 못하게 |
| **⓪ 정렬 보너스** | 집게를 물체 바로 위(`0.15`)에 맞추면 `+0.3`. 첫 단계로 가는 다리 |

보너스가 이제 네 개다. 단계마다 하나씩, 다음 단계로 건너가는 다리다.

```
⓪ 정렬 +0.3 → ① 물기 +0.5 → ② 들기 +0.5 → ③ 놓기 +1.0
```

### 팔꿈치는 한 방향으로만

2장 값은 `±130`도라 팔꿈치가 **양쪽으로** 꺾였다.
사람 팔에 없는 움직임이고, 같은 지점에 가는 자세가 둘씩 생겨
탐색 공간만 넓어진다. → **`-130 ~ 0`** 으로 막았다.

막은 뒤에도 필요한 곳에 전부 닿는지 다시 쟀다.

| 검사 | 결과 |
|---|---|
| 물체 접근 (스폰 25곳) | **25 / 25**, 최악 오차 `0.028` |
| 들어올림 높이(`0.40`) | 오차 `0.029` |
| 놓을 자리 위 | 오차 `0.024` |

### 세 번째 학습 — 드디어 배웠다

```
        보상      에피소드 길이
  20,000   -1.11      588
 380,000   -0.42      593
1,100,000  -0.09      541
1,440,000  +2.15      183     ← 거의 매번 완수
```

만점은 `0.3 + 0.5 + 0.5 + 1.0 = 2.3`이다. **보상 2.15는 거의 매번 성공**한다는 뜻이고,
에피소드 길이 183은 3000스텝 한도의 **6%** 만에 끝낸다는 뜻이다.

> 보상 곡선이 -1에 붙어 있으면 **환경을 의심**하고,
> 올라오기 시작하면 그때부터 보상과 하이퍼파라미터를 만진다.
> 이 순서를 지키지 않아 800만 스텝을 날렸다.

## 8. 물체도 놓을 자리도 매번 랜덤

4장에서는 놓을 자리가 **고정**이었다. 5장에서는 둘 다 흔든다.

```csharp
Vector3 objLocal = RandomSpot();     // 물체
MovePlaceTarget(objLocal);           // 놓을 자리 (물체와 0.6 이상 떨어뜨린다)
```

> **왜 고정하면 안 되는가**
> 놓을 자리가 늘 같으면 에이전트는 **그 자리를 통째로 외워버린다.**
> 관측을 읽지 않고도 성공하니, 겉보기 성적은 좋은데 아무것도 배우지 못한다.
> 둘 다 흔들어야 "**관측을 읽고 목표로 간다**"를 배운다.

500회 뽑아 확인했다.

| 항목 | 결과 |
|---|---|
| 물체 · 놓을 자리 | 둘 다 거리 `1.20~2.40`, 좌우 `±60°` 전 구간 |
| 둘 사이 최소 간격 | `0.604` (기준 `0.6`) |
| 너무 가까운 경우 | `0`회 |
| 작업 범위 밖 | `0`회 |

## 9. 한 번 옮기고 끝내지 않는다 — 반복 과제

성공할 때마다 에피소드를 끝내면 한 판에서 배우는 것이 **한 번**뿐이다.
게다가 매번 같은 자리에서 시작하니 늘 비슷한 상황만 본다.

그래서 **놓기에 성공하면 목표만 새 랜덤 위치로 옮기고 계속 시킨다.**

```csharp
void StartNextRound()
{
    placeTarget.position = 새 랜덤 자리;   // 물체는 방금 놓은 곳에 그대로

    _hasGrabbed = _grabRewarded = _liftRewarded = _approachRewarded = false;
    _previousDistance = DistanceToGoal();
}
```

| | 끝내면 | 이어가면 |
|---|---|---|
| 한 판의 경험 | 1회 | 여러 회 |
| 물체 시작 위치 | 항상 새 랜덤 | **직전에 자기가 놓은 자리** |
| 실제 작업과 | 멀다 | 가깝다 (옮기고 또 옮긴다) |

> **단계 보너스를 되돌리는 것을 빼먹으면 안 된다.**
> 두 번째 사이클부터 보너스가 없으면
> "한 번만 하고 가만히 있는 것"이 이득이 되어버린다.

### 성적표가 바뀐다

이제 성공해도 에피소드가 끝나지 않으므로 **에피소드 길이로는 잘하는지 알 수 없다.**
대신 "한 판에 몇 번 옮겼는가"를 직접 기록한다.

```csharp
Academy.Instance.StatsRecorder.Add("Task/Cycles", _roundCount);
```

TensorBoard에 `Task/Cycles`로 나타난다. **내가 만든 지표를 올리는 법**이다.

## 10. 갈 수 없는 곳으로 밀린 물체는 포기한다

팔이 물체를 밀고 다니다 보면 **집을 수 없는 자리**로 밀려난다.
그러면 에이전트는 갈 수 없는 곳을 향해 3000스텝을 헛돈다. (timeout)

**"팔 길이 안"이라고 집을 수 있는 게 아니다.**
집게는 물체 위에서 내려와야 하므로 실제 작업 범위는 훨씬 좁다. 실측했다.

| 거리 | 집게를 물체 위로 보낼 수 있나 |
|---|---|
| `0.80` ~ `1.00` | **불가** (팔이 너무 접힌다) |
| **`1.10` ~ `2.70`** | **가능** (좌우 ±90°까지 확인) |

→ 작업 범위를 **거리 `1.05`~`2.65`, 좌우 `±100°`** 로 잡고,
벗어나면 `-0.5` 주고 판을 새로 연다.

```
테이블 아래로 떨어졌다   → 포기
너무 가까이 밀렸다       → 포기   ← 새로 추가
너무 멀리 밀렸다         → 포기   ← 새로 추가
옆으로 크게 돌아갔다     → 포기   ← 새로 추가
```

---

### 관절 속도도 절반으로

2장 값(어깨 `120` · 팔꿈치 `180` · 좌우 `120` 도/초)은 손으로 조작할 때는
시원했지만, 물리 집게를 단 뒤로는 너무 빠르다.
빠르게 다가가면 집게가 물체를 **쳐서 날려버리고**, 급정거하면 관성으로 빠진다.

→ `60 / 90 / 60` 도/초. 실제 로봇 모터에 가깝다.
과제 전체에 10초면 충분하고 한 에피소드는 60초라 여유가 많다.

## 11. 병렬 학습 — 영역을 25개로 복제한다

강화학습이 느린 이유는 계산이 무거워서가 아니라
**경험을 모으는 속도가 느려서**다. 팔 하나로는 1초에 50스텝뿐이다.

```
메뉴 > RobotArms > 학습 영역 복제 (병렬 학습)     25개로 늘린다
메뉴 > RobotArms > 학습 영역 되돌리기 (1개로)      원래대로
```

**학습 코드는 한 줄도 바꾸지 않는다.**
ML-Agents는 `Behavior Name`이 같은 에이전트를 모두 **한 두뇌**로 묶는다.
경험이 25배로 쌓이므로 그만큼 빨리 배운다.

| | 값 |
|---|---|
| 배치 | `5 x 5`, 간격 `7.0 x 6.5` |
| 영역 간 최소 거리 | `6.5` (테이블 `5.0 x 4.0` 이므로 겹치지 않는다) |
| 화면 UI | 첫 영역만 켠다 (25개가 겹쳐 그리면 못 읽는다) |

> 컴퓨터가 버거우면 `ParallelTraining.cs`의 `AreaCount`와 `Columns`를
> `9`와 `3`으로 줄인다. **학습 코드는 어느 쪽이든 그대로다.**

> 복제는 **1~5장 구성을 모두 마친 뒤 마지막에** 한다.
> 장별 메뉴는 이름으로 부품을 찾으므로, 복제본이 있으면 첫 영역만 고친다.

## 12. 관측 16개 → **19개**

| 관측 내용 | 개수 |
|---|---|
| (4장과 같은 16개. 단 "팔 끝" → **"손가락 사이"**) | 16 |
| 얼마나 오므라들었는가 (`GripValue`) | 1 |
| 왼쪽 손가락이 닿았는가 | 1 |
| 오른쪽 손가락이 닿았는가 | 1 |

**접촉 2개가 핵심이다.** 자석일 때는 "가까이 가기만" 하면 됐지만,
이제는 손가락 사이에 물체가 들어오도록 정확히 맞춰야 한다.
접촉 정보가 없으면 AI는 **"거의 다 왔는데 한쪽만 닿았다"** 와
**"완전히 빗나갔다"** 를 구분할 수 없다.

`GripValue`가 필요한 이유는 더 미묘하다.
물체를 문 채로 오므리면 손가락이 **중간에서 멈춘다.**
즉 **덜 오므라들었다 = 뭔가 물고 있다**는 단서가 된다.

## 13. ★ 접촉 판정 — 트리거 콜백을 쓰지 않는다

처음에는 `OnTriggerEnter`로 만들었는데 **전혀 감지되지 않았다.**

```
물체가 테이블 위에서 멈춰 있으면 물리 엔진이 sleep 상태로 재운다.
잠든 물체에는 콜라이더를 밀어 넣어도 충돌/트리거 이벤트가 오지 않는다.
```

학습 중에는 물체가 거의 항상 잠들어 있다. → **영영 잡을 수 없다.**

그래서 콜백을 기다리지 않고 **매 스텝 직접 겹침을 검사**한다.

```csharp
Physics.OverlapBoxNonAlloc(center, half, _hits, rotation, ~0, QueryTriggerInteraction.Collide);
```

물체의 `sleepThreshold`도 `0`으로 두어 아예 잠들지 않게 한다.

## 14. 검증해둔 것

물리는 "될 것 같다"로 넘어가면 안 된다. 전부 돌려서 확인했다.

| 항목 | 결과 |
|---|---|
| 스폰 구역 전수 도달 (5거리 × 5좌우) | 전 지점 오차 `≤ 0.028`, 통과 방지 지켜도 동일 |
| 집어서 `0.5m` 들어올리기 (25지점) | **25 / 25 성공** |

| 들 수 있는 무게 | **`2.0` kg 까지** (물체는 `0.2` kg — 10배 여유) |
| 손을 펴면 | 물체가 `0.604` → `0.100` **중력으로 떨어진다** |

> **"세게 휘두르면 빠진다"가 버그가 아니라 목표다.**
> 4장의 자석은 아무리 휘둘러도 안 빠졌다. 그게 가짜였다는 뜻이다.

## 16. 잘 안 될 때

| 증상 | 먼저 볼 것 |
|---|---|
| **보상이 -1에서 꿈쩍 안 한다** | 진전 보상이 0이라는 뜻 = 팔이 물체 쪽으로 못 간다. **`clearance`부터 본다 (7절).** 어깨 높이(`0.30`)에 가까우면 팔이 갇힌다 |
| **보상이 -100 아래로 폭주한다** | 끝나지 않는 실패 상황이 있다. 물체가 테이블 밖으로 떨어지면 거리가 계속 멀어진다. **실패 종료 조건**을 넣는다 (7절) |
| `Value Loss`가 100을 넘는다 | 보상 크기가 들쭉날쭉하다. 한 스텝 진전 보상에 상한을 건다 |
| 에피소드 길이가 항상 최대값 | 한 번도 성공한 적이 없다. 단계 보너스가 끊겨 있지 않은지 본다 |
| 다가가면 물체가 도망간다 | 옆에서 직진하고 있다. **물체 위로 먼저** 가도록 보상을 고친다 (7절) |
| **물었는데 들면 미끄러진다** | **손가락이 너무 가볍다 (6절).** 마찰·힘을 올려도 안 고쳐진다 |
| 손가락이 물체를 통과한다 | 집게를 `Tip`의 자식으로 매달지 않았는가 (3절) |
| 물체가 옆으로 튀어나간다 | 손가락 면이 물체와 나란한가 (5절). 비스듬하면 밀어낸다 |
| 조금만 어긋나도 못 잡는다 | 경첩을 판보다 바깥에 두어 깔때기를 만들었는가 (5절) |
| 물체가 테이블에 들러붙어 있다 | `PM_Grip`을 **물체에도** 붙이지 않았는가 (6절) |
| 손가락이 테이블을 판다 | `clearance`가 `0.22`인가 (4절) |
| 접촉이 항상 `False` | 트리거 콜백에 의존하고 있지 않은가 (8절) |
| 각도가 `NaN`이다 | 물리 스텝을 한 번도 안 돌렸으면 `NaN`이다. Play 후에도 그렇다면 두 손가락의 **회전축이 서로 반대**가 아닌지 본다 |
| 아무리 가도 안 물린다 | 거리를 팔 끝이 아니라 `GripCenter`로 재고 있는가 |

## 17. 이 장에서 배우는 것

| 개념 | 내용 |
|---|---|
| **운동학과 물리를 섞는 법** | Transform으로 움직이는 것 아래에 Rigidbody를 매달면 안 된다 |
| **`MovePosition`** | 순간이동과 "이번 스텝에 여기까지"는 물리적으로 완전히 다르다 |
| **구조가 과제를 결정한다** | 손목이 없으면 옆에서 집을 수 없다. 보상을 아무리 고쳐도 안 된다 |
| **다단계 과제** | 단계마다 목표점 하나. 보상 공식은 하나로 유지한다 |
| **검증 조건 = 실제 조건** | 통과 방지를 끄고 검증했더니, 켠 채 돌아간 학습이 통째로 실패했다 |
| **학습 로그 읽는 법** | 보상이 안 움직이고 에피소드 길이가 최대값 고정 = 환경을 의심할 때다 |
| **병렬 학습** | 코드를 고치지 않고 경험을 25배로. Behavior Name이 같으면 한 두뇌다 |
| **모양이 곧 성능이다** | 깔때기 하나로 허용 오차가 `±0.06` → `±0.09`로 늘었다 |
| **계수부터 올리지 않기** | 마찰·힘을 아무리 키워도 안 되던 것이 무게 하나로 풀렸다 |
| **무게 비율** | 관절로 이은 부품끼리는 무게를 10배 안쪽으로 맞춘다 |
| **물리 이벤트를 믿지 않기** | 잠든 Rigidbody는 트리거를 발생시키지 않는다 |
| **한 번에 하나씩** | 팔은 그대로 두었기에 두 장의 학습 곡선을 비교할 수 있다 |

# 2장 — 관절 회전 구성

> **목표**: 키보드로 관절 3개를 돌려서, **사람이 직접** 물체까지 팔을 가져갈 수 있게 한다.
> **예상 시간**: 1~2시간
> **ML-Agents**: 아직 나오지 않는다

아직 AI는 없다. **사람이 조작하는 팔**을 먼저 완성한다.

---

## 1. 붙일 것

Unity 메뉴에서 **`RobotArms > 2. 관절 제어 붙이기`** 를 누르면 끝난다.
직접 하려면 `Base` 오브젝트에 컴포넌트 2개를 붙인다.

| 컴포넌트 | 스크립트 | 하는 일 |
|---|---|---|
| `RobotArmController` | `Scripts/RobotArmController.cs` | 팔의 "몸". 관절을 돌린다 |
| `ManualArmDriver` | `Scripts/ManualArmDriver.cs` | 키보드 입력을 컨트롤러에 전달한다 |
| `ArmControlHud` | `Scripts/ArmControlHud.cs` | 화면에 조작법과 관절 각도를 표시한다 |

### `RobotArmController` 설정

| 항목 | 값 | 설명 |
|---|---|---|
| Tip | `Tip` 오브젝트 | 팔 끝 |
| Reach | `2.7` | 링크 길이의 합 |
| Spawn Distance Range | `(1.2, 2.4)` | 물체가 나타나는 거리 |
| Spawn Yaw Range | `(-60, 60)` | 물체가 나타나는 좌우 각도 |
| Spawn Height | `0.1` | 물체가 테이블 위에 놓인 높이 |
| Block Penetration | `✓` | 바닥·물체 통과 방지 (아래 3절) |
| Floor Height | `0` | 테이블 윗면 높이 |
| Clearance | `0.07` | 바닥에서 띄울 여유 |
| Obstacles | `[Object]` | 뚫으면 안 되는 물체 |
| Obstacle Radius | `0.16` | 물체를 감싸는 구의 반지름 |
| Tip Exempt Distance | `0.28` | 팔 끝 근처는 물체 검사 제외 |

### 관절 설정 (Joints)

| # | Label | Pivot | Axis | Min | Max | Max Speed | Start | 키 |
|---|---|---|---|---|---|---|---|---|
| 0 | 어깨 | `J1` | (-1, 0, 0) | `-10` | `100` | `120` | `45` | `Q` / `A` |
| 1 | 팔꿈치 | `J2` | (-1, 0, 0) | `-130` | `0` | `180` | `-60` | `W` / `S` |
| 2 | 좌우 회전 | `J0` | (0, 1, 0) | `-120` | `120` | `120` | `0` | `E` / `D` |

`Label`은 화면 UI에 표시할 이름이다.

> **배열 순서가 계층 순서와 다르다**
> 계층에서는 `J0`가 맨 위(Base 바로 아래)에 있지만, 배열에서는 맨 뒤에 둔다.
>
> **배열 순서 = 액션 순서 = 키보드 순서**이기 때문이다.
> 사람이 가장 많이 쓰는 어깨·팔꿈치를 앞쪽 키에 두는 편이 조작하기 편하다.
> 3장에서 AI의 액션 번호도 이 순서를 따른다.

> **Axis가 왜 (-1, 0, 0) 인가**
> X축(+1, 0, 0) 기준으로 돌리면 각도가 +일 때 팔이 **아래로** 내려간다.
> 축을 뒤집어 두면 **각도가 +일 때 위로 올라가서** 사람이 이해하기 쉽다.
> 숫자의 부호가 직관과 맞는지 확인하는 것도 설계의 일부다.

### `ManualArmDriver` 설정

| 항목 | 값 |
|---|---|
| Distance To | `Object` |
| Success Distance | `0.25` |

## 2. 핵심 — 각도를 "변수"로 들고 있는다

이 장에서 가장 중요한 부분이다.

```csharp
// 관절마다 현재 각도를 float 변수로 보관한다
Angle += 입력값 × maxSpeed × Time.fixedDeltaTime;
Angle  = Mathf.Clamp(Angle, minAngle, maxAngle);   // 범위 밖으로 못 나가게

pivot.localRotation = Quaternion.AngleAxis(Angle, axis);
```

### ① 왜 Transform의 회전을 읽지 않고 변수로 따로 갖는가

`transform.localEulerAngles`는 Unity가 항상 `0 ~ 360`으로 정리해서 돌려준다.
`-10°`로 설정해도 읽으면 `350°`가 나온다.
**그러면 관절 제한(Clamp)을 걸 수가 없다.**

각도를 내 변수로 들고 있으면 `-10`은 그냥 `-10`이다.
Transform은 "그려주는 역할"만 맡긴다.

### ② 왜 각도를 직접 넣지 않고 "속도"로 더해 나가는가

입력을 각도 그 자체로 쓰면 팔이 한 프레임 만에 순간이동하듯 튄다.
**속도로 조금씩 더해 나가면** 자연스럽게 이어지는 움직임이 나온다.

> 이 방식이 중요한 진짜 이유는,
> **3장에서 AI의 행동(Action)을 바로 이 자리에 끼워 넣을 것이기 때문**이다.
>
> ```
> 2장:  Angle += 키보드입력 × maxSpeed × dt
> 3장:  Angle += AI의액션   × maxSpeed × dt      ← 숫자의 출처만 바뀐다
> ```
>
> 팔 입장에서는 누가 명령했는지 구분하지 않는다. 그래서 그대로 재사용된다.

### ③ 각속도(`Velocity`)를 같이 기록해둔다

```csharp
Velocity = (Angle - 직전Angle) / deltaTime;
```

지금은 안 쓰지만 **3장의 관측에 들어간다.**
"지금 얼마나 빨리 움직이는 중인지"를 AI가 알아야 목표를 지나쳐 버리지 않는다.
RollerBall이 공의 속도를 관측에 넣은 것과 같은 이유다.

### ④ 관측에 쓸 값을 미리 만들어둔다

컨트롤러는 나중에 AI가 쓸 값들을 **정규화해서** 내놓는 함수를 갖고 있다.

| 함수 | 내놓는 값 |
|---|---|
| `NormalizedAngle(i)` | 관절 각도 ÷ 180 |
| `NormalizedVelocity(i)` | 관절 각속도 ÷ 최대속도 |
| `ToNormalizedLocal(위치)` | 받침대 기준 로컬 좌표 ÷ reach |
| `SpawnPointLocal(거리, 좌우각)` | 테이블 위 한 점 |

전부 **-1 ~ 1 근처**로 맞춰서 나온다.
각도(±180)와 위치(±2.7)처럼 단위가 다른 값을 그냥 섞으면
크기가 큰 값이 학습을 지배해버리기 때문이다.

## 3. 관절 각도 범위만으로는 부족하다 — 바닥·물체 통과 방지

### 문제

관절마다 `min ~ max` 각도를 정해두었다. 그런데 이걸로는 부족하다.

```
어깨(J1)   =  20°    ← 범위 -10 ~ 100 안
팔꿈치(J2) = -120°   ← 범위 -130 ~ 0 안
```

**두 각도 모두 자기 범위 안에 있는데, 팔 끝은 테이블 아래로 내려간다.**

실제로 방지 기능을 끄고 어깨를 끝까지 내린 뒤 팔꿈치를 접어보면,
팔 끝 높이가 **-0.732** 까지 내려간다. 테이블을 그냥 통과해 버린다.

> ### 여기서 배우는 것
> **가동 범위는 관절 하나만으로 정해지지 않는다.
> 관절들의 "조합"에 따른 제약이 따로 있다.**
>
> 실제 산업용 로봇도 마찬가지다.
> 각 축의 리미트와 별개로 "작업대를 치지 않는 자세인가"를 따로 검사한다.

### 해결 — 움직인 뒤에 검사하고, 어기면 되돌린다

```csharp
public void Drive(int i, float normalizedSpeed, float deltaTime)
{
    bool wasBlocked = IsBlocked();        // 움직이기 전 상태를 기억
    float before = joints[i].Angle;

    joints[i].Drive(normalizedSpeed, deltaTime);

    if (!wasBlocked && IsBlocked())       // 이번 움직임 때문에 뚫렸다면
        joints[i].ResetTo(before);        // 되돌린다
}
```

`IsBlocked()`는 팔의 뼈대(J0 → J1 → J2 → Tip)를 이은 선분을
여러 점으로 쪼개서, 각 점이

1. 바닥(`floorHeight + clearance`)보다 낮은가
2. 물체를 감싸는 구(`obstacleRadius`) 안에 들어왔는가

를 확인한다.

### 세 가지 설계 포인트

**① 왜 "막는" 것이 아니라 "되돌리는" 것인가**

미리 안전한 각도를 계산해서 막으려면 역기구학을 풀어야 한다.
**일단 움직여보고, 아니면 취소한다.** 훨씬 단순하고 결과는 같다.
`ResetTo`는 각속도도 0으로 만들어서, 벽에 닿아 멈춘 것처럼 보인다.

**② 왜 "움직이기 전에도 막혀 있었는지"를 확인하는가**

어쩌다 막힌 자세로 들어갔을 때, 모든 움직임을 되돌리면
**영영 빠져나올 수 없게 된다.**
이번 움직임 **때문에** 새로 뚫린 경우에만 되돌린다.

**③ 왜 팔 끝 근처는 물체 검사에서 제외하는가**

물체를 통째로 "들어가면 안 되는 구역"으로 잡으면,
**물체를 집으러 다가가는 것 자체가 막힌다.**
`tipExemptDistance`(0.28) 안쪽은 검사하지 않아서,
팔 끝은 물체에 닿을 수 있고 팔뚝은 물체를 관통하지 못한다.

### 검증 결과

| 테스트 | 결과 |
|---|---|
| 방지 **끄고** 어깨 내리고 팔꿈치 접기 | 팔 끝 높이 **-0.732** (뚫림) |
| 방지 **켜고** 무작위 조작 20,000스텝 | 팔 전체 최저 높이 **0.070** (= 한계선), 뚫림 **0회** |
| 방지 **켜고** 극단 8조합 전수 | 최저 높이 **0.085**, 전부 통과 |

## 4. 키보드 조작과 화면 UI

### 조작 키

| 키 | 동작 |
|---|---|
| `Q` / `A` | 어깨 올리기 / 내리기 |
| `W` / `S` | 팔꿈치 올리기 / 내리기 |
| `E` / `D` | 좌우 회전 |
| `R` | 자세 초기화 |
| `F1` | 조작법 UI 켜기 / 끄기 |
| `Space` | 잡기 — 4장부터 쓴다 |

RollerBall과 같은 새 Input System(`Keyboard.current`)을 쓴다.

조작 키는 `Scripts/RobotArmInput.cs` 한 곳에 모아두었다.
**화면에 표시할 키 이름도 같은 파일에 있다.**
따로 두면 키를 바꿨을 때 안내 문구가 어긋나기 때문이다.
**3장의 `Heuristic()`도 똑같이 이 파일을 쓴다.**

### 화면 UI

Play하면 화면 왼쪽 위에 이런 패널이 뜬다.

```
┌─────────────────────────────────┐
│ 로봇 팔 조작                     │
│                                 │
│ Q / A    어깨          45.0°    │
│ W / S    팔꿈치       -60.0°    │
│ E / D    좌우 회전      0.0°    │
│                                 │
│ R        자세 초기화             │
│ Space    잡기 (4장부터)          │
│                                 │
│ 팔 끝 ↔ 물체   1.04             │
└─────────────────────────────────┘
F1 : 조작법 숨기기
```

| 표시 | 의미 |
|---|---|
| 관절별 **현재 각도** | 지금 몇 도인지 실시간 |
| `(최소)` `(최대)` | 가동 범위 끝에 닿았을 때 |
| `팔 끝 ↔ 물체` | 거리. `0.25` 안으로 들어오면 초록색 `도달!` |
| `바닥·물체에 막혀 멈춤` | 3절의 통과 방지가 작동했을 때 빨간색으로 |

> **왜 각도를 화면에 띄우는가**
> 팔을 눈으로만 보면 "지금 어깨가 몇 도인지" 알 수 없다.
> 숫자를 보면서 움직여야 **가동 범위가 어디까지이고,
> 어떤 조합에서 바닥에 걸리는지** 훨씬 빨리 감이 온다.
>
> 3장에서 AI가 보게 될 값(관절 각도)을 사람도 똑같이 보는 셈이다.

> **구현 메모**
> `Canvas`나 프리팹 없이 `OnGUI`만으로 그린다. 씬에 오브젝트를 더
> 만들지 않아서 2장의 초점이 흐려지지 않는다.
> 한글이 깨지지 않도록 운영체제 폰트(`Malgun Gothic` 등)를 직접 불러온다.

## 5. 확인 ★ 이 장의 전부

Play를 누르고 직접 조작해본다.

- [ ] 화면 왼쪽 위에 **조작법 패널**이 뜬다 (`F1`로 켜고 끌 수 있다)
- [ ] 팔을 움직이면 패널의 **각도 숫자가 실시간으로 바뀐다**
- [ ] 키보드로 팔을 자유롭게 움직일 수 있다
- [ ] `E` / `D` 로 팔이 **좌우로 돈다** (턴테이블이 같이 돈다)
- [ ] `R` 로 시작 자세(45°, -60°, 0°)로 돌아간다
- [ ] 가동 범위 끝에서 더 눌러도 팔이 넘어가지 않는다
- [ ] **어깨를 끝까지 내리고 팔꿈치를 접어도 팔이 테이블을 뚫지 않는다**
      (이때 패널에 빨간색 `바닥·물체에 막혀 멈춤` 이 뜬다)
- [ ] **팔뚝이 물체를 관통하지 않는다** (팔 끝은 물체에 닿을 수 있다)
- [ ] `Block Penetration`을 꺼보면 **실제로 뚫린다** — 이 기능이 왜 필요한지 직접 확인
- [ ] Scene 뷰에 Gizmo가 보인다 — **흰 구 = 도달 범위, 초록 부채꼴 = 물체가 나타나는 구역,
      빨간 원 = 팔이 내려갈 수 있는 한계 높이, 빨간 구 = 뚫을 수 없는 물체**
- [ ] **초록 부채꼴이 흰 구 안쪽에 들어 있다**
- [ ] **물체까지 팔 끝을 가져갈 수 있다** → Console에 `[RobotArms] 도달!` 이 찍힌다
- [ ] `Object`를 부채꼴 안 아무 데나 옮겨도 **전부 닿을 수 있다**

> ### 사람이 못 하면 AI도 못 한다
> 마지막 세 항목이 이 장의 존재 이유다.
>
> 여기서 안 되는데 3장으로 넘어가면, 학습이 안 될 때
> "보상 설계가 틀렸나 / 관측이 부족한가 / 하이퍼파라미터 문제인가"를
> 끝없이 의심하게 된다. **원인은 환경인데 말이다.**
>
> 안 되면 고칠 것: 관절 가동 범위, 링크 길이, 물체가 나타나는 거리·각도 범위.

## 6. 이 장에서 배우는 것

| 개념 | 내용 |
|---|---|
| **관절 1개 = 입력 1개** | 3장에서 그대로 "액션 1개"가 된다 |
| **가동 범위(Clamp)** | 실제 로봇의 하드웨어 제약을 코드로 표현하는 법 |
| **조합에 따른 제약** | **관절 각도 범위만으로는 바닥 통과를 막을 수 없다** |
| **변화량으로 제어** | 입력은 "상태"가 아니라 **변화량**으로 주는 것이 안전하다 |
| **정규화** | 단위가 다른 값을 -1~1로 맞춰야 학습이 안정적이다 |
| **환경 검증** | 학습을 시작하기 전에 사람이 먼저 풀어본다 |

### 통과 방지가 3장 이후에 왜 중요한가

사람은 팔이 테이블을 뚫으면 "아, 잘못됐네" 하고 피한다.
**AI는 그렇지 않다.** 보상만 오르면 테이블을 뚫고 지나가는 지름길을
기꺼이 학습한다. 물리적으로 불가능한 동작을 배워버리는 것이다.

환경 단계에서 **애초에 불가능한 동작을 못 하게** 막아두면,
AI는 실제로 가능한 동작 안에서만 답을 찾는다.
이것도 "학습 환경을 만든다"는 말의 일부다.

### 왜 이 장을 따로 두는가

RollerBall에서는 `Heuristic()`이 "있으면 편한 기능" 정도였다.
로봇 팔에서는 다르다.

**팔은 관절 각도 조합에 따라 닿을 수 있는 영역이 정해져 있고,
그 영역은 눈으로 봐서는 잘 모른다.**
숫자(길이, 각도 범위)를 조금만 잘못 잡아도 물체에 영원히 못 닿는 환경이 된다.

그래서 **AI를 붙이기 전에 사람이 먼저 풀어보는 단계**를 독립된 장으로 둔다.

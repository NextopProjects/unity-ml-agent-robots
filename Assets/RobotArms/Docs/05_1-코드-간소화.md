# 5.1장 — 코드 간소화

> **5장이 이 교재의 최종 결과물이다.**
> 여기까지 오는 동안 코드는 계속 늘어나기만 했다.
> 이 장에서는 **아무 기능도 추가하지 않고** 코드를 절반으로 줄인다.

## 왜 줄이는가

기능을 만들 때와 남에게 보여줄 때는 좋은 코드가 다르다.

```
만드는 중   — 잘게 나눈다.  어디가 잘못됐는지 하나씩 짚어봐야 하니까
완성한 뒤   — 합친다.      읽는 사람은 "무엇을 하는가"만 알면 되니까
```

5장은 **만드는 중**이었다. 손가락이 물체를 통과하고, 물었는데 미끄러지고,
각도가 `NaN`이 되는 문제를 하나씩 잡아야 했다. 그래서 스크립트를 셋으로 나눴다.

지금은 다 끝났다. 그런데 이 상태로 두면 처음 보는 사람은
**파일 3개를 오가며 같은 손가락 목록을 세 번 본다.**

> ### 초보자용 코드의 기준
> **"이 줄을 지우면 무엇이 안 되는가?"** 에 답할 수 없으면 지운다.
> 언젠가 쓸지도 모르는 값, 항상 `true`인 스위치, 서로 같은 두 변수가 그렇다.

## ① 스크립트 3개를 1개로

셋 다 **같은 오브젝트(`Hand`)에 붙어 있었다.** 나뉘어 있을 이유가 이미 사라져 있었다.

```
[5장]                                 [5.1장]
Hand ├── GripperHand    팔 끝 따라가기      Hand ── Gripper  ← 하나
     └── PincerGripper  손가락 여닫기
FingerL ── FingerContact  닿았나            FingerL  (스크립트 없음)
FingerR ── FingerContact  닿았나            FingerR  (스크립트 없음)
```

합친 `Gripper.cs`가 하는 일은 셋뿐이다. 파일을 열면 이 세 줄이 바로 보인다.

```
① 팔 끝을 따라간다   FixedUpdate()
② 손가락을 여닫는다   Drive(bool close)
③ 닿았는지 알려준다   UpdateContacts()
```

### 연결할 칸이 절반으로

| 5장 | 5.1장 |
|---|---|
| `GripperHand` : follow, yawReference, fingers[2] | `Gripper` : follow, yawReference, target, |
| `PincerGripper` : fingerL, fingerR, contactL, contactR | fingerL, fingerR |
| `FingerContact` × 2 : target | |
| **연결 10개** | **연결 5개** |

손으로 따라 만들 때 **잘못 꽂을 자리가 절반으로 줄었다.**
이게 이 장의 가장 큰 이득이다.

## ② 서로 같은 변수 찾아 없애기

5장의 에이전트에는 이런 코드가 있었다.

```csharp
bool _hasGrabbed;     // 한 번이라도 물었는가
bool _grabRewarded;   // 물기 보상을 줬는가
```

```csharp
if (nowHolding && !_isHolding)
{
    _hasGrabbed = true;
    if (!_grabRewarded) { AddReward(grabReward); _grabRewarded = true; }
}
```

둘은 **언제나 같은 값**이다. 같은 순간에 켜지고, 같은 곳에서 함께 꺼진다.
하나면 된다.

```csharp
if (!_grabbed) AddReward(grabReward);
_grabbed = true;
```

> **변수가 둘인데 값이 항상 같다면, 그건 둘이 아니라 하나다.**
> 이런 쌍은 기능을 덧붙이다 보면 쉽게 생긴다.

같은 방법으로 없앤 것들:

| 없앤 것 | 왜 없어도 되나 |
|---|---|
| `_grabRewarded` | `_hasGrabbed`와 값이 항상 같다 |
| `_successCount` | `_roundCount`와 겹친다. 화면에는 "이번 판 n회"만 보이면 된다 |
| `useDenseReward` | 5장에서는 항상 `true`다. 꺼보는 실험은 3장에서 이미 했다 |
| `PincerGripper.Closing` | 아무도 읽지 않는다 |
| `closeSignL/R` | 구조상 `+1`/`-1`로 고정이다. 인스펙터에 둘 이유가 없다 |
| 에이전트의 `spawnDistanceRange` | **팔이 이미 갖고 있다.** ↓ |

### 같은 값을 두 군데 두지 않는다

물체가 나타나는 범위(거리 1.2~2.4, 좌우 ±60°)를 **팔과 에이전트가 따로** 갖고 있었다.

Scene 뷰의 초록 부채꼴은 **팔이 가진 값**으로 그린다.
에이전트가 다른 값을 쓰고 있으면, **화면에 보이는 것과 실제가 달라도 알 수가 없다.**

```csharp
// 5.1장 — 범위는 팔에게 물어본다
Vector3 RandomSpot() => arm.SpawnPointLocal(
    Random.Range(arm.spawnDistanceRange.x, arm.spawnDistanceRange.y),
    Random.Range(arm.spawnYawRange.x, arm.spawnYawRange.y));
```

## ③ "지금 자세를 기억했다가 되돌리기"를 쓰지 않는다

에피소드가 시작되면 손가락을 활짝 벌린 자리로 되돌려야 한다.
5장은 이렇게 했다.

```csharp
// Awake() — 시작할 때의 자세를 기억해 둔다
_restPosL = transform.InverseTransformPoint(_bodyL.position);
_restRotL = Quaternion.Inverse(transform.rotation) * _bodyL.rotation;
```

**이 코드는 씬을 어떤 모습으로 저장했느냐에 결과가 달라진다.**
손가락이 반쯤 오므려진 채로 저장되어 있으면, 그 자세가 "쉬는 자세"가 된다.
매 판 반쯤 오므린 채로 시작하니 물체가 들어올 자리가 없다.

실제로 이 교재를 만들면서 밟았다. 잡기 검증을 물리 엔진으로 돌린 **뒤에**
씬을 저장했더니, 테스트가 끝난 자세가 그대로 박혔다.
패드 간격이 `0.622`(활짝)여야 하는데 `0.308`(반쯤 오므림)이었다.

5.1장에서는 **자세를 숫자 두 개로 못 박는다.**

```csharp
public float fingerOffset = 0.17f;  // 손목 중심 ~ 경첩
public float openAngle = 50f;       // 이만큼 벌어진 상태가 쉬는 자세다

Restore(_bodyL, -fingerOffset, -openAngle);
Restore(_bodyR, +fingerOffset, +openAngle);
```

씬이 어떤 상태로 저장되어 있든 **언제나 같은 자세**로 돌아온다.
덤으로 캐시 변수 4개(`_restPosL/R`, `_restRotL/R`)가 사라졌다.

> **"현재 상태를 기억해서 되돌린다"는 편해 보이지만, 기준이 데이터에 숨는다.**
> 되돌릴 자리를 아는 코드라면 그 자리를 **직접 적는 편이** 언제나 안전하다.

## ④ 만질 값과 만지면 안 되는 값을 나눈다

5장의 에이전트는 인스펙터에 값이 **25개**였다. 처음 보면 어디를 건드려야 할지 알 수 없다.

```csharp
[Header("보상 — 여기만 바꿔가며 실험한다")]
public float approachReward = 0.3f;   // ⓪ 물체 위에 정렬했다
public float grabReward     = 0.5f;   // ① 물었다
public float liftReward     = 0.5f;   // ② 들었다
public float placeReward    = 1.0f;   // ③ 놓았다
public float dropPenalty    = 0.3f;   // 엉뚱한 곳에서 놓쳤다
public float lostPenalty    = 0.5f;   // 작업 범위 밖으로 보냈다

// 아래는 실측으로 정한 값이다. 바꾸면 팔이 물체에 닿지 못한다.
const float LiftHeight = 0.40f;
const float WorkMin = 1.05f;
...
```

`const`로 바꾸면 세 가지가 한꺼번에 해결된다.

- 인스펙터가 깨끗해진다 (**25개 → 11개**)
- 씬 구성 메뉴에서 대입할 줄이 사라진다 (**45줄 → 27줄**)
- **"이건 건드리지 말라"는 말을 코드가 대신한다**

> 실측값을 인스펙터에 두면, 누군가 슬라이더를 만지는 순간
> 문서에 적힌 숫자와 씬의 숫자가 달라진다. 그러면 검증 기록이 거짓말이 된다.

## 확인 체크리스트

- [ ] 콘솔에 에러가 없다 (깨진 스크립트 0개)
- [ ] `Hand`에 붙은 스크립트가 **1개**다

- [ ] 팔이 시작 각도(`45 / -60 / 0`)로 서 있다
- [ ] `BehaviorParameters`의 관측이 **19**, 연속 **3**, 이산 **1** 그대로다
- [ ] `Space`로 물체를 집어 들 수 있다
- [ ] 5장에서 만든 `.onnx`를 `Model` 칸에 넣고 `Inference Only`로 돌려도 똑같이 움직인다

## 검증 결과

**바꾼 뒤에도 잡기 성능이 그대로인지 실제로 재봤다.**
스폰 구역을 거리 5칸 × 좌우 5칸 = **25곳**으로 훑으면서,
위로 접근 → 내려오기 → 오므리기 → 들어올리기를 물리 엔진으로 돌렸다.

```
blockPenetration = True   clearance = 0.14   (실제 학습과 같은 조건)
판정 = 양쪽 접촉 유지 + 물체 높이 >= 0.40  (에이전트의 ② 단계 조건 그대로)

거리 1.2 :  들었음  들었음  들었음  들었음  들었음
거리 1.5 :  들었음  들었음  들었음  들었음  들었음
거리 1.8 :  들었음  들었음  들었음  들었음  들었음
거리 2.1 :  들었음  들었음  들었음  들었음  들었음
거리 2.4 :  물기만  들었음  들었음  들었음  들었음

물기 25/25   들어올리기 24/25   가장 낮았던 물체 높이 0.428
```

> 거리 2.4 · 좌우 -60도 한 곳에서 물긴 했는데 0.40까지 못 올렸다.
> **집게 문제가 아니라 검증용 컨트롤러의 한계다.** 정기구학 전수 스캔으로는
> 그 자리에서 물체를 `1.331`까지 올릴 수 있다. 관절을 하나씩 흔들어 보고
> 좋은 쪽으로 가는 단순한 방식이라 어깨와 팔꿈치를 동시에 써야 하는 자세를
> 못 찾는 것이다. 학습한 에이전트는 이걸 해낸다.

> ### 검증 조건이 실제 조건과 같아야 한다
> 첫 줄의 `blockPenetration = True`가 중요하다.
> 5장에서는 편하자고 이걸 **끈 채로** 검증했다. 전부 통과했다.
> 학습은 켠 채로 돌았고, **800만 스텝을 통째로 날렸다.**
> 그래서 검증 코드가 실제 설정을 그대로 출력하게 만들어 두었다.

## 이 장에서 배우는 것

1. **만들 때 나누고, 끝나면 합친다.** 나눈 상태 그대로 두는 것이 항상 옳지는 않다.
2. **값이 항상 같은 변수 두 개는 하나다.** 기능을 덧붙이다 보면 이런 쌍이 생긴다.
3. **같은 값을 두 군데 두지 않는다.** 둘이 어긋나면 화면에 보이는 것이 거짓말이 된다.
4. **바꿔도 되는 값만 인스펙터에 둔다.** `const`는 "건드리지 말라"는 표시다.
5. **되돌릴 자리는 직접 적는다.** 현재 상태를 기억하면 기준이 데이터에 숨는다.
6. **정리한 뒤에는 다시 잰다.** 안 재면 조용히 반 토막 나 있어도 모른다.
7. **물리를 돌려본 씬은 그대로 저장하지 않는다.** 시험이 끝난 자세가 처음 모습이 된다.

> 5.1장에서는 관측도 액션도 보상 공식도 **한 글자도 바꾸지 않았다.**
> 그래서 5장에서 학습한 두뇌가 그대로 동작한다.
> **리팩터링이란 "밖에서 본 모습이 같은 것"을 말한다.**
